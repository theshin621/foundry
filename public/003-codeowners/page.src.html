CODEOWNERS — who actually gets requested?

Paste your CODEOWNERS file and the paths a pull request touches. For every file you get the rule that won, the owners GitHub would request, and the rules that matched but lost — plus the lines GitHub silently skips. Free, no signup, and it never leaves your browser.

How the decision is made. GitHub's rule is one line long and catches almost everyone: “Order is important; the last matching pattern takes the most precedence.” Not the most specific pattern — the last one. A rule with no owners still wins; it just leaves the file unowned, which is how you carve an exception out of a broader rule.

What this cannot know. GitHub also requires each owner to exist and to have write access — “if you specify a user or team that doesn't exist or has insufficient access, a code owner will not be assigned.” This page has no access to your org, so it checks the format of an owner and never its existence. A row here can name an owner GitHub would not actually request.

Where the matching comes from. The pattern semantics are ported line-for-line from hmarr/codeowners (MIT, © 2020 Harry Marr), pinned at commit 11d3ff2659b769bcb43ddef81a6ab19d1205d9c2, and checked against its own test corpus and against a differential harness that re-answers the same pattern/path pairs with the real Go implementation. Two divergences are known and deliberate: a malformed line is skipped here (GitHub's documented behaviour) rather than aborting the whole file, and the pattern / — which crashes the reference implementation — is reported as matching nothing.

What it refuses, and why it refuses it at the door. Every dimension that drives work is measured before anything is split, parsed or compiled: the size of each box (1 MiB), the number of lines (20,000 rules, 5,000 paths), the length of a line (4,096 characters here, 1,024 for a path) and the length of a single whitespace-delimited field (256 characters — a pattern and an owner are both fields). That last one is the limit this page was missing: ** @ followed by 100,000 a is a legal-looking 100 KB line that cost 23.7 seconds, because one absurd owner was re-drawn once per matching file. Counting is done in a single pass that allocates nothing and stops at the first violation, so refusing that input now costs 0.007 ms; scanning a full 1 MiB box that passes every limit costs 9 ms.

Where this deliberately refuses rather than copying the reference. The reference implementation reads its file with Go's bufio.Scanner, which silently drops any line of 65,536 bytes or more — and then abandons every rule after it, so a single over-long line can change the owner of a file thousands of lines further down with no error anywhere. This page refuses at 4,096 characters instead, which is strictly inside that boundary (4,096 characters cannot exceed 16,384 bytes in UTF-8), so it can never reach the case where it would quietly disagree. Refusing loudly and diverging silently are not the same thing, and only one of them is safe.

Why it can't hang. Patterns are compiled to a non-backtracking automaton, not to a JavaScript RegExp, so no input can trigger catastrophic backtracking. Because linear time still is not bounded time, every stage that costs anything — reading the file, compiling each pattern, matching, and drawing — is metered against one shared wall clock, and past 500 ms of work this page says it cannot evaluate rather than answering from a half-finished pass. The answer itself is bounded by construction rather than by that meter: at most 1,000 rows, 20 owners per rule, 10 losing rules per file and 1,000,000 characters of drawn output in total, whichever binds first — the counts in the summary are computed over everything you pasted, and the page says so whenever it draws less than it counted. Every append is a complete row, and the tags that close the answer come out of a reserve the cap cannot consume — because the first version of this bound filled mid-row, left dangling cells, and had the browser's own error recovery quietly push the result 117 characters past the limit it was advertising.

The input limits are not the work limit. The numbers above are the largest inputs this page will read. Whether it can finish depends on rules × paths, because every path is tested against every rule, and that is a property of your machine as much as of your input. Measured on 2026-08-05: 200 rules against 500 files — 100,000 pairs, larger than most real pull requests — answered 5/5 times in at most 417 ms on the machine that built this, while an independent run of the identical input on a slower two-core machine refused it every time. 300 × 500 refused 1 time in 5 here; 500 × 500 refused every time on both. So there is no honest fixed pair-count to quote — around 100,000 pairs is where it starts to matter, and past roughly 250,000 it will not answer at all. Which is why the page prints its own measured time under every answer instead of asking you to trust a number somebody measured once, somewhere else.

The timing number is measured, not claimed. Under every answer this page prints the real time from starting work to the browser having painted the result, taken across two animation frames so it includes the paint and not merely the JavaScript. Across 24 trials of the four heaviest inputs available to it, that measurement ranged from 517 ms to 641 ms — always above the 500 ms work meter, because drawing the refusal happens after the meter has already stopped, and worst at the input that is cheapest to evaluate and most expensive to have received. An earlier version of this page advertised a ceiling measured with a JavaScript timer that stopped before the browser drew anything and was wrong by 810 ms; the version before this one quoted a single 550 ms reading that a second measurement immediately beat. The number above is a range over repeated trials for that reason.

One cost this page does not control. That measurement starts when this page starts working, which is after the browser has accepted your paste. Pasting a megabyte of text into a plain <textarea> is itself work the browser does before any script runs: a 1 MiB file of ordinary CODEOWNERS lines costs it about half a second, and 1 MiB consisting only of newlines — a million empty lines to lay out — cost roughly 17 seconds in the same test, none of it ours and none of it avoidable from here. Said plainly rather than quietly excluded from a number.
