### 1. `npm-publish-preflight` — EVERGREEN — **RECOMMENDED**

**What:** paste your `package.json`, your `.npmignore`/`.gitignore` and your file list; see the
exact set of files `npm publish` will put in the tarball, and for every file the *one rule that

**Why it exists:** the precedence between `files[]`, `.npmignore`, `.gitignore` and npm's own
always-in/always-out lists is genuinely confusing, and the failure is silent and public: people
ship `.env` and `node_modules`, or publish a package with `dist/` missing, and only find out
after the version is immutable on the registry.

**Occupant hunt — run fresh today, three searches, empty at the web-tool layer.** What exists is
documentation and CLI: npm's own docs, the npm/cli *Files & Ignores* wiki, npm's 2017
"Publishing what you mean to publish" post, the "don't use .npmignore" essay, and CLI-only
workarounds (`npm pack --dry-run`, `pure-publish`, the `npmignore` package). No page takes the
four inputs and shows you the resolved set with per-file reasons. `npm pack --dry-run` is the
closest thing and it (a) needs the project checked out locally, (b) gives you a file list with
no *why*, and (c) is exactly the step people skip.

**Structural edge:** whole-resolution vs one-rule, and *reasons* vs a bare list. No signup, no
install, nothing leaves the browser — which matters, because the input is your private tree.

**Promo motive:** none. No vendor benefits from me believing this; the sources are npm's own docs
and a nine-year-old complaint thread.

**Day-build gate: PASS.** Static page, no API key, no account, no marketplace, no review.
Borrow-don't-build satisfied twice over: the *semantics* are published rules (three citations
below) and the *matcher* already exists in this repo — `lib/nfa.js`, proven linear-time.

**Rules pinned to primary sources (the checker re-verifies these, not my memory):**

- Always included, any case/extension: `package.json`, `README`, `LICENSE`/`LICENCE`, the file
  in `main`, the file(s) in `bin`.
  — <https://docs.npmjs.com/cli/v11/configuring-npm/package-json>
- Always ignored: `*.orig`, `.*.swp`, `.DS_Store`, `._*`, `.git`, `.hg`, `.lock-wscript`,
  `.npmrc`, `.svn`, `.wafpickle-N`, `CVS`, `config.gypi`, `node_modules`, `npm-debug.log`,
  `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`.
  Of those, a hard core **cannot be re-included even if named explicitly**: `.git`, `.npmrc`,
  `node_modules`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lockb`.
  — same page.
- `.npmignore` **replaces** `.gitignore`, it does not merge with it: "If there is a `.gitignore`
  file, and `.npmignore` is missing, `.gitignore`'s contents will be used *instead*." An **empty**
  `.npmignore` therefore turns `.gitignore` off entirely.
  — <https://docs.npmjs.com/cli/v11/using-npm/developers/> and
    <https://github.com/npm/cli/wiki/Files-&-Ignores>

  will be included, regardless of `.npmignore` settings" — flagged in npm's own wiki as a known
  issue (#11669) rather than intended design. The page states this *and* labels it as npm's open
  bug, because a tool that quietly picks the "right" answer over the shipped one is lying.
  — <https://github.com/npm/cli/wiki/Files-&-Ignores>

  file away (`p === mainTarget`, `p === browserTarget`, `bins.indexOf(p)`, `p === 'package.json'`).
* The case-fold *introduced* a defect that did not exist before it: lowering the whole string
  **before** tokenising desynchronises fixed-width tokens from the string when a fold changes
  length — Turkish dotted `İ` becomes two characters, so `a?c` stops matching `aİc`.

That is not "nearly there". That is the same generator producing new defects at the rate they are
being closed, which is exactly what killed ship 003 and exactly what the clause exists to stop.

**Why `failed` and not `killed`.** `failed` is the status Amendment 2026-08-02 clause 6 added for
this case — a checker-FAILed build is neither staged nor killed, and mislabelling it either way
corrupts the ledger. Ship 003 was *killed* after three builds and seven verdicts across three days;
ship 006 is one build and four verdicts in one day. The candidate is recorded as failed and, per the
clause, **does not re-enter tomorrow as a rebuild**. Only Theshin can overturn that.

**Nothing from this ship is merged, deliberately — including `lib/`.** Ship 003's engineering *was*
merged to `main` because it had been proven correct and only the product around it had failed. That
is not true here: **two of the six live defects are inside `lib/gitignore.js` and `lib/npmpack.js`
themselves** (the Unicode fold, and ancestor-pruning ordering ahead of the `files[]` branch). Merging
them would put known-defective code into the shared library where the *next* ship inherits it
silently. The branch `ship/006-npm-publish-preflight` stays in the repo, dark and unmerged, as the
record. What is worth salvaging from it, and the only condition under which it should be:

* `lib/checks/npm-publish-oracle.json` — **43 reference cases, 33 of them verified against a real
  `npm pack --dry-run` on npm 10.9.7**, plus the six round-2 findings as ready-made failing cases.
  That corpus is correct and is the most valuable thing this run produced.
* The six named defects below are a *specification* for a correct npm publish-set resolver. Anyone
  building one should start from them rather than rediscover them.

**The residual, named exactly (six items, none speculative — every one has a reproducing input):**

1. force-include comparisons must be case-folded like everything else (`main`, `browser`, `bin`, `package.json`)
2. case folding must happen **per token**, not by lowering the whole string, or length-changing
   Unicode (`İ`, final sigma) desynchronises fixed-width tokens
3. ancestor pruning must run **after** the `files[]` branch, not before it — `files[]` outranks a
   user ignore rule and the page currently contradicts its own documentation
4. a UTF-8 BOM must be stripped from an ignore file's first line, or rule 1 is silently dead
5. the *shallowest* excluding ancestor must be cited, not whichever ancestor the hard-list happened
   to hit first — otherwise the citation is fabricated even when the verdict is right
6. symlinks are never packed by npm, and `git ls-files` — which this page's own placeholder
   recommends — lists them; the gap must be handled or disclosed

**A methodological finding worth more than the ship.** Round 1's 23-case oracle passed 23/23 and
was still wrong about npm's single most pervasive behaviour, because the maker wrote both the
matcher and the cases. Every defect that mattered in both rounds came from one move: **install the
real implementation and diff against it.** The rule now in `lib/README.md`: *where a real
implementation exists, diff against it — a maker's own oracle proves only that the code agrees
with the maker.*
