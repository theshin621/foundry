## 2. The defect: `health.json` asserts a browser behaviour and measures a substring

`.github/workflows/health-check.yml` derives the field as:

```python
return {..., 'has_beacon': "'/_b'" in body}
```

A raw substring test on the response bytes. Under BOTTLENECKS #1's third clause — *"for
liveness-of-markup claims the oracle executes the page in a real browser and observes the behaviour
itself; hand-written parse-and-match walkers are FORBIDDEN"* — this field is not permitted to exist
in its current form. It reports `true` for a snippet sitting inside `<template>`, `<noscript>`, an
HTML comment, or a `<script type="application/json">`: every vector incidents #4 and #009 already
paid for, all four of which leave the string `'/_b'` in `body` and the beacon dead.

This is not hypothetical for this field. Its own inline comment records that it *already failed this
exact way once* — until 2026-08-10 it matched `cloudflareinsights.com`, a third-party beacon ship
008 had removed, so **every page reported `has_beacon: true` while the field measured a script the
loop no longer depended on.** The string was changed; the method that made the lie possible was not.

And today's round-1 result proves the naive replacement is also wrong: a browser-truth oracle that
does *not* neutralise `navigator.webdriver` returns a confident **false RED** on a perfectly live
beacon. Both failure directions are now empirically demonstrated, before a line of code exists.
